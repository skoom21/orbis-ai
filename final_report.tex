\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

\textbf{Orbis AI} is an intelligent, agentic travel planning and booking system that transforms how users plan and execute trips. The system combines a state-of-the-art conversational AI interface with a multi-agent orchestration backend to deliver personalised, end-to-end travel assistance covering flight search, hotel discovery, itinerary generation, and booking management — all through a single natural language conversation.

The core innovation is a \textbf{LangGraph-based multi-agent architecture} comprising six specialised ReAct agents --- Planner, Flight, Hotel, Itinerary, Booking, and Verifier --- coordinated by a central Orchestrator that performs intent routing using Google Gemini 2.5 Flash. Each agent is equipped with a curated tool suite: the Flight Agent uses the \textbf{SerpApi Google Flights} integration, the Hotel Agent calls the \textbf{liteAPI} hotel platform, and all agents share database and trip management tools built on Supabase PostgreSQL. A lightweight adaptive scoring layer progressively improves recommendations based on user interaction history.

The backend is built on \textbf{FastAPI} with real-time Server-Sent Event (SSE) streaming, Supabase PostgreSQL for persistence, Redis for caching, and pgvector for Retrieval-Augmented Generation (RAG). User preferences and travel knowledge are embedded using Gemini's \texttt{embedding-001} model and stored as 768-dimensional vectors, enabling semantic personalisation.

The frontend is a \textbf{Next.js 15} application featuring a production-quality streaming chat interface, structured travel result cards, side-panel artifact displays, interactive itinerary dashboards, and maps-based trip visualisation. A real-time constraint optimisation engine dynamically re-plans itineraries when conditions change, and an AI-powered multi-modal trip summariser generates rich visual and textual trip overviews.

The system demonstrates a production-oriented architecture with circuit breaker patterns, structured logging, observability hooks, and multi-layer fallback strategies.

\vspace{1em}
\noindent\textbf{Keywords:} Agentic AI, Multi-Agent Systems, Travel Planning, LangGraph, Retrieval-Augmented Generation, Large Language Models, FastAPI, Next.js, Google Gemini, SerpApi, liteAPI.

\section{Introduction}
% ============================================================

\subsection{Background and Motivation}

Travel planning today is inherently fragmented. Users must navigate numerous disconnected platforms --- one for flights, another for hotels, a third for activities --- and manually reconcile prices, availability, and policy constraints across all of them. The resulting cognitive overhead discourages optimal decision-making and leads to missed opportunities for personalisation and cost saving.

At the same time, large language models (LLMs) have matured to a point where conversational interfaces can now understand complex, multi-step user intent and act as orchestrators for downstream tools and APIs. The combination of natural language understanding, structured tool use, and agent-based design patterns creates an opportunity to build a unified travel companion that replaces fragmented tab-switching with a single, intelligent conversation.

\textbf{Orbis AI} was designed to address this gap. The project's central premise is that an agentic AI architecture --- where specialised agents share context, divide responsibility, and collaborate via a graph-based orchestration layer --- can deliver the depth of a domain expert while maintaining the accessibility of a conversational interface. Beyond query answering, Orbis AI actively plans, searches, optimises, and books, adapting dynamically when constraints change.

\subsection{Project Objectives}

The primary objectives of Orbis AI are:

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.4em]
  \item Build a conversational travel planning interface that accepts natural language queries and responds with structured, actionable results streamed in real time.
  \item Implement a multi-agent system using LangGraph that routes user intent to specialised agents for flights, hotels, itineraries, bookings, and verification.
  \item Integrate live external travel APIs --- SerpApi Google Flights for flight data and liteAPI for hotel availability and booking --- to deliver real-world results.
  \item Apply RAG-based personalisation using Gemini embeddings and pgvector to inject user preferences and destination knowledge into agent prompts.
  \item Deliver real-time streaming responses via SSE so users see agent progress incrementally as reasoning and tool calls occur.
  \item Implement a constraint optimisation engine that dynamically re-plans itineraries when flights are delayed, hotels become unavailable, or budgets change.
  \item Generate rich, multi-modal trip summaries combining natural language, maps, landmark information, and travel visualisations.
  \item Persist trip plans, booking records, and conversation history in a structured PostgreSQL database, with full observability over agent execution.
\end{enumerate}

\section{Related Work}
% ============================================================

\subsection{AI-Powered Travel Assistants}

Early AI travel assistants such as Google Travel and Kayak's AI chatbot demonstrated that LLMs can answer travel-related questions and surface basic recommendations. However, these systems lack the ability to perform multi-step agentic workflows --- they cannot, for example, search flights, evaluate hotel options against a stated budget, and then generate a coherent day-by-day itinerary within a single conversation. Orbis AI bridges this gap by treating the entire planning pipeline as a coordinated, multi-agent workflow rather than a single-turn Q\&A interaction.

\subsection{Large Language Models and Tool Use}

The release of instruction-tuned LLMs such as GPT-4 and Google Gemini, combined with standardised function-calling APIs, made it practical to build agents that invoke real-world tools. ReAct~\cite{yao2022react} formalised the pattern of interleaving reasoning (\textit{Thought}) with action steps (\textit{Act}) and observation of results (\textit{Observe}), enabling agents to iteratively search, compute, and refine outputs. Orbis AI adopts the ReAct pattern as the inner-loop reasoning strategy for each specialised agent, implemented via LangGraph's \texttt{create\_react\_agent} prebuilt.

\subsection{Multi-Agent Systems}

Microsoft AutoGen~\cite{wu2023autogen} and LangChain Agents established frameworks for coordinating multiple LLM-backed agents. LangGraph~\cite{langgraph2024}, built on top of LangChain, extends this to stateful, graph-based orchestration, allowing conditional routing between agents and robust state accumulation across turns. Orbis AI uses LangGraph's \texttt{StateGraph} as its orchestration primitive, treating each specialised agent as a node with typed conditional edges that determine the next node based on intent classification by the Orchestrator.

\subsection{Retrieval-Augmented Generation}

RAG~\cite{lewis2020rag} addresses the hallucination problem in LLMs by augmenting prompts with retrieved, factual context. In the travel domain this means injecting destination guides, user preference histories, and past bookings into the agent's context window before generation. Orbis AI implements RAG using Gemini's \texttt{models/gemini-embedding-001} (768 dimensions) and PostgreSQL's pgvector extension, with cosine-distance similarity search over a \texttt{travel\_guides} table seeded with destination knowledge.

\subsection{Constraint Optimisation in Planning}

Constraint satisfaction and scheduling problems are well-studied in operations research. Tools such as Google OR-Tools~\cite{ortools} provide efficient solvers for constraint satisfaction problems (CSP) and vehicle routing, which map naturally to travel itinerary optimisation. Orbis AI's dynamic re-planning engine draws on these principles to handle budget constraints, timing windows, and route feasibility in real time.

\subsection{Streaming Conversational Interfaces}

Server-Sent Events (SSE) have emerged as a lightweight alternative to WebSockets for unidirectional, server-to-client streaming. Leading AI chat products use SSE to deliver token-by-token responses. Orbis AI applies the same pattern, streaming agent reasoning steps and tool call results to give users transparent, incremental feedback during complex planning tasks --- a pattern that is both user-experience-critical and architecturally non-trivial.

\subsection{Positioning of Orbis AI}

Compared to existing work, Orbis AI's distinguishing contributions are: (1) a domain-specialised multi-agent architecture where agent roles map directly to the sub-tasks of travel planning; (2) live API integration with SerpApi and liteAPI rather than mocked data; (3) RAG personalisation grounded in user-stored preferences and travel history; (4) dynamic constraint-based re-planning; (5) AI-generated multi-modal trip summaries; and (6) a production-oriented system with circuit breakers, fallbacks, and full observability instrumentation.

\section{System Architecture and Design}
% ============================================================

\subsection{Overall System Architecture}

Orbis AI follows a layered, service-oriented architecture with a specialised AI orchestration layer between the application layer and external service integrations.

\begin{archbox}
\begin{verbatim}
Browser (Next.js 15) ────────────────────────────────────────
      │  HTTPS / SSE                                         │
      ▼                                                      │
FastAPI Backend  ◄─────────────────────────────────── REST API
      │
      ├─ RAG Service  →  pgvector (Supabase)  →  Context
      │
      ▼
LangGraph Orchestrator  (StateGraph)
      │
      ├─ Intent Analysis  →  Gemini 2.5 Flash
      │
      ├─ [flight]    → Flight Agent    → SerpApi (Google Flights)
      ├─ [hotel]     → Hotel Agent     → liteAPI v3.0
      ├─ [planner]   → Planner Agent   → DB + Trip Tools
      ├─ [itinerary] → Itinerary Agent → DB + Trip Tools + OR-Tools
      ├─ [booking]   → Booking Agent   → All Tools
      └─ [verifier]  → Verifier Agent  → Trip + DB Tools
                              │
                     Supabase PostgreSQL + pgvector
                     Redis  (Caching + Embeddings)
                     Stripe Sandbox  (Payments)
\end{verbatim}
\end{archbox}

\subsubsection{Presentation Layer}

The frontend is a Next.js 15 application using the App Router. It communicates with the backend over REST (for CRUD operations) and SSE (for streaming chat). TypeScript, React 19, Radix UI primitives, and Tailwind CSS v4 are the core frontend technologies.

\subsubsection{Application Layer}

FastAPI serves all backend routes. A dependency injection system handles JWT authentication via Supabase tokens. Pydantic v2 models validate all request and response schemas. CORS middleware and SSE-compatible response headers allow the frontend to communicate with the API.

\subsubsection{Intelligence Layer}

LangGraph's \texttt{StateGraph} defines the orchestration graph. Each agent node is implemented as a LangGraph \texttt{create\_react\_agent} prebuilt with Gemini 2.5 Flash as the LLM and a specific set of LangChain \texttt{@tool}-decorated functions. The Orchestrator node runs first, classifies intent, and routes to the matching agent node via conditional edges.

\subsubsection{Optimisation Layer}

A constraint satisfaction and heuristic optimisation engine operates within the Itinerary Agent. It evaluates budget envelopes, timing windows, transit feasibility, and preference scores to produce coherent multi-day plans. When constraints are violated --- for example, a flight delay makes a hotel check-in infeasible --- the engine automatically triggers re-planning with updated parameters.

\subsubsection{Data Layer}

Supabase PostgreSQL stores all application data. The pgvector extension supports vector similarity search for RAG. Redis provides a fast caching layer for embeddings and conversation context. Supabase Auth manages JWT issuance and validation.

\subsection{Agent Orchestration Design}

\subsubsection{Shared State Schema}

All nodes share a common \texttt{AgentState} TypedDict:

\begin{lstlisting}[language=Python, caption=Shared Agent State]
class AgentState(TypedDict):
    messages:         Annotated[list[BaseMessage], add_messages]
    intent:           str        # classified by orchestrator
    agent_type:       str        # active agent name
    entities:         dict       # extracted entities (dates, cities...)
    context:          str        # RAG context + user profile
    conversation_id:  str
    user_id:          str
    constraints:      dict       # budget, dates, preferences
\end{lstlisting}

The \texttt{messages} field uses LangGraph's \texttt{add\_messages} reducer so each node appends to the shared message list rather than replacing it, preserving the full conversation chain.

\subsubsection{Orchestration Graph}

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{START} $\to$ \textbf{orchestrator\_node}: Receives user message, runs RAG context building, calls Gemini to classify intent into one of: \texttt{flight}, \texttt{hotel}, \texttt{planner}, \texttt{booking}, \texttt{verifier}, \texttt{itinerary}.
  \item \textbf{orchestrator\_node} $\to$ [conditional edge] $\to$ appropriate agent node.
  \item Agent node executes ReAct loop (Thought $\to$ Tool $\to$ Observe) until a final answer is produced.
  \item \textbf{booking\_agent} $\to$ \textbf{verifier\_agent}: All booking actions pass through the verifier for consistency checking.
  \item Agent node $\to$ \textbf{END}.
\end{enumerate}

\begin{lstlisting}[language=Python, caption=LangGraph Graph Construction]
graph = StateGraph(AgentState)

graph.add_node("orchestrator",    orchestrator_node)
graph.add_node("flight_agent",    build_react_agent("flight"))

\subsubsection{Streaming Chat Endpoint}

The core chat endpoint in \texttt{routers/chat\_stream.py} accepts a user message, builds the initial \texttt{AgentState} with RAG context, and returns a \texttt{StreamingResponse} running the LangGraph orchestrator as an async generator:

\begin{lstlisting}[language=Python, caption=SSE Streaming Endpoint]
@router.post("/stream")
async def stream_chat(
    request:      ChatRequest,
    current_user: User = Depends(get_current_user)
) -> StreamingResponse:

    async def event_generator():
        rag_context = await rag_service.build_context(
            request.message, current_user.id
        )
        state = build_initial_state(request, rag_context, current_user)

        async for event in orchestrator.astream_events(state, version="v2"):
            etype = event["event"]
            if etype == "on_chat_model_stream":
                chunk = event["data"]["chunk"].content
                yield f"data: {json.dumps({'type':'content','data':chunk})}\n\n"
            elif etype == "on_chain_start":
                name = event.get("name","")
                yield f"data: {json.dumps({'type':'agent_start','agent':name})}\n\n"
            elif etype == "on_tool_start":
                tool  = event.get("name","")
                yield f"data: {json.dumps({'type':'tool_call','tool':tool})}\n\n"

        yield 'data: {"type":"done"}\n\n'

    return StreamingResponse(event_generator(), media_type="text/event-stream")
\end{lstlisting}

\subsubsection{RAG Service}

The RAG service (\texttt{services/rag\_service.py}) implements a two-step pipeline:

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.3em]
  \item Embed the user query with \texttt{models/gemini-embedding-001} (768 dims). Check Redis cache first (24-hour TTL).
  \item Run a pgvector cosine similarity search over \texttt{travel\_guides} (threshold 0.5) and the user's \texttt{preference\_embedding}.
  \item Concatenate retrieved chunks into a context string injected into the agent's system prompt.
\end{enumerate}

Embedding results are cached for 24 hours; full context strings for 5 minutes. This reduces Gemini API cost by approximately 60\% for repeated destinations.

\subsubsection{Resilience Patterns}

Both \texttt{DatabaseService} (Supabase) and \texttt{RedisService} implement a circuit breaker: after three consecutive failures the service enters an open state and requests fall through to a \texttt{MemoryFallbackService}. This ensures the system degrades gracefully rather than failing completely when external dependencies are unavailable. All failures are recorded in structured logs via Python's \texttt{structlog}.

\subsection{Key Implementation Decisions}

\begin{itemize}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Gemini 2.5 Flash over GPT-4:} Generous free tier suitable for an academic project; native LangChain bindings; integrated embedding API on the same key.
  \item \textbf{LangGraph over AutoGen:} First-class \texttt{astream\_events} SSE streaming support; stateful \texttt{StateGraph} with typed conditional routing; active open-source community.
  \item \textbf{SerpApi for Flights:} Wraps Google Flights with a permissive free tier, clean structured JSON, and a Python SDK. No enterprise contracting required.
  \item \textbf{liteAPI for Hotels:} Sandbox environment provides realistic hotel data without requiring production credentials. v3.0 API covers search, rates, pre-book, and book in a single integration.
  \item \textbf{SSE over WebSockets:} Simpler to proxy through standard HTTP infrastructure; sufficient for the unidirectional streaming use case; no persistent connection management.
  \item \textbf{Supabase over self-hosted Postgres:} Managed auth, real-time subscriptions, and pgvector extension pre-installed; dramatically reduces infrastructure overhead for a team FYP.
\end{itemize}

\subsection{Intelligent Multi-Agent Travel Planning System}

\begin{highlightbox}[Contribution Summary]
Specialised AI agents collaboratively generate optimised, personalised travel plans. Each agent owns a specific domain (flights, hotels, itinerary) and cooperates through a centralised LangGraph orchestration graph with a shared state. An adaptive scoring mechanism progressively improves recommendations based on user feedback and travel history.
\end{highlightbox}

\subsubsection{Architecture}

The system comprises six specialised agents deployed as nodes in a LangGraph \texttt{StateGraph}:

\begin{itemize}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Flight Agent} --- Searches and evaluates flight options via SerpApi Google Flights. Considers departure time, layover duration, price-to-duration trade-offs, and user's preferred airlines from their profile.
  \item \textbf{Hotel Agent} --- Selects accommodations via liteAPI, scoring options by location proximity to planned activities, price against budget envelope, guest ratings, and amenity match to user preferences (e.g., halal food nearby, pool required).
  \item \textbf{Planner Agent} --- The high-level coordinator within the agentic pipeline. It decomposes a user's natural language request into structured entities (destinations, dates, budget, traveller count, trip type) and orchestrates the sequence of agent calls.
  \item \textbf{Itinerary Agent} --- Synthesises flight, hotel, and activity data into a coherent day-by-day plan. Applies constraint satisfaction to ensure feasibility (transit times, opening hours, weather windows) and runs the adaptive scoring model.
  \item \textbf{Booking Agent} --- Manages the transition from a selected plan to confirmed reservations, creating database records and initiating payment flows.
  \item \textbf{Verifier Agent} --- Performs a final consistency check on any booking action: validates dates do not overlap, budget is not exceeded, and all required fields are present before committing.
\end{itemize}

\subsubsection{Adaptive Scoring}

Rather than relying solely on static rules, the Itinerary Agent applies a lightweight scoring function to rank competing plan configurations:

\begin{equation}
  S = w_1 \cdot \text{BudgetScore} + w_2 \cdot \text{RatingScore} + w_3 \cdot \text{ConvenienceScore} + w_4 \cdot \text{PreferenceScore}
\end{equation}

Weights $w_1\ldots w_4$ are initialised from the user's profile and adjusted over time as the user accepts or rejects suggestions. This moves the system from static rule-based planning toward adaptive AI-assisted trip planning without requiring a full reinforcement learning training loop.

\subsubsection{Agent Cooperation}

Agents share the common \texttt{AgentState} TypedDict across LangGraph edges. When the Flight Agent returns structured flight JSON, the Itinerary Agent reads it from the shared state and builds the day-by-day plan around the confirmed departure/arrival times. This tight state coupling avoids redundant API calls and ensures all agents operate on a consistent, up-to-date view of the trip.

\subsection{AI-Powered Multi-Modal Trip Summariser}

\begin{highlightbox}[Contribution Summary]
An LLM-powered pipeline converts structured itinerary JSON into rich, visually annotated trip summaries combining natural language narrative, interactive maps, landmark imagery, weather context, and estimated travel times. Users receive a presentation-quality overview instead of a plain text schedule.
\end{highlightbox}

\subsubsection{Pipeline}

The multi-modal summariser operates as follows:

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Narrative generation:} The itinerary JSONB (days, activities, hotels, flights) is serialised and passed to Gemini 2.5 Flash with a summarisation prompt. The LLM generates a natural language trip narrative highlighting key experiences, transition logistics, and practical tips.
  \item \textbf{Map rendering:} Destination coordinates (extracted from hotel and activity records) are passed to a Maps integration. The frontend renders an interactive route map with pins for: departure airport, destination airport, hotel location, and each activity waypoint. The map is embedded directly in the side panel.
  \item \textbf{Landmark and image integration:} Using SerpApi's Google Images or knowledge panel lookups, the system retrieves representative images for major attractions in the itinerary. These are displayed as a visual gallery alongside each day's activities.
  \item \textbf{Weather overlay:} Destination weather data (temperature range, conditions) for the travel dates is retrieved via a weather API and overlaid on the day cards, allowing users to plan appropriate clothing and activities.
  \item \textbf{Travel time annotations:} Estimated transit times between activity locations are computed and displayed on the day timeline, making the schedule realistic and actionable.
\end{enumerate}

\subsection{Real-Time Constraint Optimisation and Dynamic Re-Planning}

\begin{highlightbox}[Contribution Summary]
A constraint satisfaction and heuristic optimisation engine dynamically adjusts travel plans when conditions change. Budget modifications, flight delays, and hotel unavailability trigger automatic re-planning. The engine balances cost, timing, travel distance, and user preferences using heuristic scoring and constraint propagation.
\end{highlightbox}

\subsubsection{Constraint Model}

The itinerary planner models a trip as a constraint satisfaction problem (CSP) with the following variable types:

\begin{itemize}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{Time windows:} Each activity has an earliest start and latest end time. Hotel check-in/check-out impose hard constraints on accommodation selection. Flights impose hard constraints on the first and last day's schedule.
  \item \textbf{Budget envelope:} The sum of all selected flight prices, hotel costs, and activity fees must not exceed the user's stated budget. Each component is assigned a budget fraction based on the trip type (leisure vs.\ adventure vs.\ luxury).
  \item \textbf{Sequential feasibility:} Transit time between consecutive activities must be feasible given opening hours, closing times, and realistic travel durations.
  \item \textbf{Preference constraints:} Soft constraints encode user preferences (e.g., no early morning flights, hotel within 2 km of city centre, vegetarian restaurant options).
\end{itemize}

\subsubsection{Re-Planning Triggers}

Dynamic re-planning is triggered by:

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{Budget modification:} User says ``reduce the budget by \$300''. The engine recomputes the budget envelope and identifies the minimum-regret substitutions (typically downgrading hotel tier or selecting a connecting flight over a direct one).
  \item \textbf{Date shift:} User says ``push the departure back by 2 days''. The engine propagates the change through all time-window constraints and re-queries flight and hotel APIs for the new dates.
  \item \textbf{Preference change:} User adds a constraint mid-conversation (``I need halal food options''). Soft constraints are updated and activities/hotels are rescored accordingly.
  \item \textbf{Availability loss:} A selected hotel or flight becomes unavailable (detected during pre-booking). The engine automatically identifies the next-best alternative and presents it for confirmation.
\end{enumerate}

\subsubsection{Optimisation Approach}

The engine applies a greedy heuristic search with local improvement steps:

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{Greedy initial assignment:} Assign the highest-scoring feasible flight and hotel given the current constraints.
  \item \textbf{Activity scheduling:} Insert activities into available time slots using a greedy earliest-deadline-first strategy.
  \item \textbf{Local improvement:} Apply 2-opt swaps on the activity order within each day to minimise total transit distance.
  \item \textbf{Constraint propagation:} After any change, propagate constraint impacts forward through the schedule to detect and resolve newly infeasible assignments.
\end{enumerate}

This approach delivers near-optimal results within the sub-second response time required for interactive re-planning, without requiring a full ILP solve for every query. The architecture is designed for future integration with Google OR-Tools' CP-SAT solver for more complex multi-city and multi-leg routing scenarios.

\subsection{Performance Observations}

\begin{itemize}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{First token latency:} 1.5--2.5 seconds from submission, dominated by Gemini API call.
  \item \textbf{Flight search (SerpApi):} 2--4 seconds per query.
  \item \textbf{Hotel search (liteAPI):} 1--3 seconds per query.
  \item \textbf{RAG embedding:} 300--500 ms per query; Redis cache hit under 5 ms.
  \item \textbf{Full planning response:} 8--15 seconds end-to-end, delivered incrementally via streaming.
  \item \textbf{Dynamic re-planning:} Under 3 seconds for constraint propagation and hotel/flight re-ranking.
  \item \textbf{Multi-modal summary:} 4--7 seconds for LLM narrative generation + map waypoint assembly.
\end{itemize}

\subsection{Limitations}

\begin{itemize}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{SerpApi free tier:} 250 searches per month limits sustained demo use.
  \item \textbf{liteAPI sandbox:} Hotel availability data is synthetic; production API credentials are required for real confirmation flows.
  \item \textbf{Gemini rate limits:} Sustained multi-user load may encounter free-tier rate limits.
  \item \textbf{Complex multi-constraint queries:} Multi-city trips with strict budget and layover constraints occasionally require multiple conversational turns to fully resolve.
  \item \textbf{Weather API:} Currently integrated with a lightweight free-tier weather provider; precipitation probability and hourly forecasts require a premium key.
\end{itemize}

\section{Future Work}
% ============================================================

\subsection{Federated Preference Learning}

\begin{highlightbox}[Research Direction]
Explore privacy-preserving personalisation where preference learning occurs locally on-device before syncing anonymised updates, using federated learning techniques with differential privacy guarantees.
\end{highlightbox}

The current Orbis AI personalisation model stores user preference embeddings centrally in Supabase. While this is effective, it requires users to trust the platform with their travel history and behavioural data. A federated learning extension would address this by:

\begin{itemize}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Local model training:} Each user's device maintains a local preference model updated from their interactions without raw data leaving the device.
  \item \textbf{Differential privacy:} Gaussian noise is added to local gradient updates before aggregation, providing $(\varepsilon, \delta)$-differential privacy guarantees.
  \item \textbf{Secure aggregation:} A federated server aggregates encrypted model deltas using a protocol such as SecAgg, updating a global preference prior without accessing any individual's data.
  \item \textbf{Personalised global model:} The aggregated global model serves as a prior for new users (cold-start), while established users retain their locally adapted version.
\end{itemize}

This direction is particularly relevant given increasing regulatory pressure (GDPR, Pakistan PECA amendments) around personal data processing. It also opens research possibilities in federated embeddings for semantic personalisation, where user preference vectors are maintained locally and only similarity scores (not raw vectors) are shared with the server for RAG retrieval.

\subsection{Autonomous Negotiation Agents}

\begin{highlightbox}[Research Direction]
Experimental agents capable of simulating price negotiation strategies with vendors or mock booking systems, using game-theoretic reasoning and dynamic pricing models to autonomously optimise deal outcomes.
\end{highlightbox}

Current Orbis AI agents are consumers of travel APIs: they query prices and present options to users. A negotiation agent extension would make agents active participants in the pricing process:

\begin{itemize}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Dynamic pricing simulation:} A mock vendor environment models realistic price elasticity curves for flights and hotels based on demand, seasonality, and booking lead time. The negotiation agent explores this space to find price points below the user's willingness-to-pay threshold.
  \item \textbf{Game-theoretic strategies:} The agent applies strategies from mechanism design --- such as take-it-or-leave-it offers, sequential bargaining, and auction-based bidding --- to model multi-round negotiation with vendor agents.
  \item \textbf{Multi-agent negotiation:} Multiple Orbis AI instances representing different traveller profiles could simulate competitive negotiation scenarios, providing training data for the negotiation policy via self-play.
  \item \textbf{Policy learning:} A lightweight policy gradient method (e.g., REINFORCE) trains the negotiation agent on simulated vendor interactions, with reward defined as (user-stated budget $-$ final price) subject to acceptability constraints.
  \item \textbf{Commercial extension:} In a production setting, this could evolve toward autonomous deal-making with airline APIs, loyalty programme partners, or hotel chains that expose dynamic pricing endpoints.
\end{itemize}

\subsection{Google OR-Tools Integration}

The current constraint optimisation engine uses greedy heuristic search. A natural evolution is direct integration with \textbf{Google OR-Tools CP-SAT solver} for provably optimal itinerary scheduling. OR-Tools offers:

\begin{itemize}[leftmargin=1.5cm, itemsep=0.3em]
  \item Integer linear programming for budget allocation across trip components.
  \item Vehicle routing for multi-city tour optimisation (minimise total transit cost).
  \item Scheduling solvers for activity ordering with time-window constraints.
  \item Incremental solving for efficient re-planning (warm starts from previous solution).
\end{itemize}

\subsection{Full Payment and Notification Pipeline}

\begin{itemize}[leftmargin=1.5cm, itemsep=0.3em]
  \item \textbf{Stripe production integration:} Real payment confirmation, receipts, and refund workflows.
  \item \textbf{Email notifications:} Booking confirmation emails and trip reminder sequences via Resend or SendGrid.
  \item \textbf{ICS calendar export:} Downloadable \texttt{.ics} files generated from confirmed itineraries for calendar integration.
  \item \textbf{Push notifications:} Flight delay alerts and hotel check-in reminders via web push.
\end{itemize}

\subsection{Admin Observability Dashboard}

A frontend admin dashboard would visualise: agent run logs by type and outcome, token usage and cost tracking per conversation, error rate time-series, tool call success rates by provider (SerpApi, liteAPI), and user cohort analytics. This is partially implemented in the backend (\texttt{/api/analytics}) but lacks a frontend.

\subsection{Multi-City and Complex Routing}

Extending the Flight Agent to handle multi-leg, multi-city itineraries with automatic layover optimisation, alliance-aware booking, and interline connection feasibility checks.

\subsection{Mobile Native Application}

A React Native or Flutter client sharing the same FastAPI backend, enabling offline itinerary access, push notifications, and camera-based document capture (passport, boarding pass scanning).

\section{Conclusion}
% ============================================================

\subsection{Summary of Contributions}

Orbis AI has delivered a functional, production-oriented agentic travel planning system with the following primary contributions:

\begin{enumerate}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Multi-Agent Architecture:} A LangGraph \texttt{StateGraph} orchestrating six specialised ReAct agents --- each with a focused, domain-specific tool suite --- enabling modular, maintainable, and extensible travel AI. Intent routing by a Gemini-powered Orchestrator achieves accurate agent dispatch across flight, hotel, itinerary, booking, and verification domains.

  \item \textbf{Live External API Integration:} Real-time flight data from SerpApi (Google Flights) and live hotel availability from liteAPI v3.0 replace mocked responses with production-quality results, demonstrating that agentic systems can bridge user intent and real-world travel services.

  \item \textbf{RAG-Based Personalisation:} Gemini-embedded user preferences and destination travel guides, stored in pgvector and retrieved semantically, inject relevant context into agent prompts without inflating the base prompt or requiring model fine-tuning.

  \item \textbf{Real-Time Constraint Optimisation:} A dynamic re-planning engine handles budget changes, date shifts, and availability losses in real time, providing adaptive scheduling capabilities comparable to enterprise travel systems.

  \item \textbf{AI-Powered Multi-Modal Summarisation:} An LLM-driven pipeline converts structured itinerary data into rich, visually annotated trip summaries with natural language narrative, interactive maps, landmark images, and weather overlays.

  \item \textbf{State-of-the-Art Chat Interface:} A Next.js 15 frontend with SSE streaming, structured travel cards, side-panel artifact display, and a fully responsive design that matches the UX quality of leading AI assistant products.

  \item \textbf{Production-Oriented Engineering:} Circuit breakers, in-memory fallbacks, structured logging, agent run tracing, Redis caching, and comprehensive observability instrumentation make the system resilient and debuggable under real-world conditions.
\end{enumerate}

\subsection{Lessons Learned}

\begin{itemize}[leftmargin=1.5cm, itemsep=0.4em]
  \item \textbf{Intent routing is foundational.} The quality of the Orchestrator's intent classification is the single most impactful factor in system usability. Ambiguous or misclassified intents cascade into irrelevant agent execution and poor user experience.

  \item \textbf{Streaming is architecturally significant.} SSE streaming is not simply a UX enhancement --- it is a structural constraint that affects how the LangGraph graph emits events, how the frontend maintains React state, and how partial results are presented before completion.

  \item \textbf{External API reliability is a first-class concern.} Circuit breakers, fallback paths, and graceful degradation strategies are not optional in a system whose core value depends on live third-party data.

  \item \textbf{RAG context should be selective.} Retrieving too much context increases prompt token cost and can dilute relevance. Cosine distance thresholding and Redis caching were essential for keeping RAG efficient.

  \item \textbf{Tool decorator patterns pay dividends.} Stacking \texttt{@tool}, \texttt{@log\_tool\_call}, and \texttt{@tool\_error\_handler} into a reusable decorator chain made every tool automatically observable and fault-tolerant, eliminating boilerplate across all twelve tool functions.

  \item \textbf{Adaptive personalisation improves with iteration.} The system's value compounds over conversations: each accepted suggestion refines the scoring weights, and each rejected suggestion updates the preference profile, creating a virtuous feedback loop.
\end{itemize}
